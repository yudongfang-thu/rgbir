# 项目级执行约束

1. 我们不是在写一篇安全攻防论文。你有权进行必要校验，但是禁止、禁止、禁止过度防御。
2. 禁止写哈希和 SHA256。
3. 禁止针对基本不可能出现的 case 反复编写防御性代码。
4. 需要 rubric 的地方不要过度机械化；rubric 必须服务于研究判断与执行效率。

## 计算资源使用约束

5. 本项目所有 agent、任务与子进程合计最多同时占用 3 张物理 GPU。启动时从候选卡中动态选择，不在实验配置中硬编码 GPU 编号；不得干扰、抢占或终止其他用户进程。
6. 每张被本项目使用的 GPU 上最多同时运行 2 个本项目 CUDA PID；DDP rank、训练、评估和特征提取进程均逐个计入，纯 CPU DataLoader worker 不计入。
7. 每张 GPU 上本项目进程合计显存必须严格小于该卡 `nvidia-smi` 所报总显存的 70%；94 服务器的 24,564 MiB RTX 4090 对应 `<17,195 MiB`。启动前同时检查实际空闲显存并按预计峰值预留余量。
8. 本项目所有进程的主机 aggregate RSS 必须严格小于 300 GB；当前占用加新任务预约达到 240 GB 时停止接纳新任务并排队。
9. 默认每卡只放一个正式训练。第二个进程用于评估、特征提取，或仅在 mini 实测记录证明可容纳后作为第二个正式训练。
10. 资源限制按整个项目全局计算，不按终端、screen、agent 或实验分别计算。所有训练、评估、特征提取及其 DDP rank 必须由 `tools/project_resource_guard.py` 的已绑定 lease 覆盖，launcher 必须按实际 rank 数预约 CUDA PID；旧队列中的“4 卡、每卡 4 job”规则失效，资源不足时只能排队。
11. 每个实际 run 必须用 `tools/write_jstars_run_receipt.py` 保存方法身份、数据角色、seed、实际 trainer/loss/config/命令/环境/split 副本、资源峰值、指标副本和 test exposure 状态；不写哈希。

## 文献复现与实验连续性

12. 把复现可信度与实验启动分开。缺少作者数据、split、权重、代码或超参细节，只能降低复现等级，不得单独作为停止实验的理由。
13. 在为外部方法制定计划前，必须检索论文正文与补充材料、所有作者的 GitHub 仓库、仓库 forks/releases/issues、第三方复现与方法合集、失效链接的其他作者镜像或存档。检索记录必须在计划启动前落盘。
14. 复现身份只使用四类说明：`AUTHOR-EXACT`、`PAPER-RECONSTRUCTED`、`THIRD-PARTY-RECONSTRUCTED`、`PROTOCOL-ADAPTED`。当 exact 资产不可得时，按论文、作者代码、公开数据和第三方实现做最佳努力重建，逐项报告偏差，不伪装为 exact。
15. 只有会让结果无法解释或越界的问题才允许停止对应 run：数据/标注合同错误、指标实现错误、loss 或梯度未生效、split 泄漏、读取封存测试集、资源越界、或经最小修复后仍无法运行。论文数字未完全对齐和方法负结果都是应报告的结果，不是全项目停机条件。
16. 原文复现、数据诊断和统一协议迁移是可并行的证据线。某一论文的 exact 复现受阻，不得锁死使用已有 checkpoint 的数据诊断、统一重评或其他方法复现。
17. GPU 暂时不可用时，继续完成代码、数据、配置、checkpoint 和命令预检，并将通过 canary 条件的任务放入受资源 lease 约束的等待队列；不因文档不确定性让可用 GPU 无故空置。
18. 禁止把不受本项目控制的外部依赖（作者回复、私有数据、未公开权重、失效链接或未披露细节）设为全项目的启动前置或总停止门。它们只能影响复现身份和结论强度；在公开证据足以构建可解释实验时，必须继续最佳努力复现。
19. 停止决策默认只作用于出现问题的单个 run 或单条证据线，并必须同时给出可继续的替代路径。只有全局资源越界、封存测试泄漏或数据/评估基础整体无效，才允许停止全项目实验。
20. 一项方法的复现应分成两个明确层次：先尽量在原论文的数据、split、模型和评估协议下验证其方法是否可信；再迁移到本项目统一协议下做公平比较。若原条件不可完全恢复，则降级为 reconstructed 并继续；但 adapted 结果不得冒充原文严格复现。
21. 训练结果与计划阈值不一致时，先把它视为待分析的科学结果。不得因早期 AP 低、单 seed 负增益、未达论文数字或中间指标不理想而自动停掉其他可解释的实验；先排查实现、协议和统计口径，再决定继续、修复或报告负结果。

## 数据优先的方法设计

22. 在设计新机制前，必须先用数据样张、标注特性、原生 baseline 的检测结果和特征可视化确认问题确实存在。不得先决定机制，再为机制选样或事后构造问题。
23. RGB–IR 与 Optical–SAR 的迁移难度不能仅由特征距离或少量案例判定。至少分开检查任务上限、配对 source 的真实增量，以及该增量能否由 target-only 特征达到；VEDAI、LLVIP、DroneVehicle 和 SpaceNet6 均应纳入样张与边界对比，但根据各自的标注和 test exposure 身份限定其证据用途。
24. 新方法只解决已被证据确认的失败模式，首先用最小实现和低成本消融验证其因果贡献。若问题不存在或机制无增益，应保留负结果并转向下一个有证据的假设，不堆叠 method zoo。
