原 RGB/IR 的 3.47/3.70 小时是完整 200 轮的 **CSV 累计训练时间**，不是含独立评价、排队与全部进程启动的完整任务墙钟。当前 C1 的 18.172 小时仅累计到第 59 个已完成轮次，不能写成完整 E200 耗时。其最近十轮实际范围为 1071.2–1160.3 秒（17.85–19.34 分钟），中位数 18.529 分钟；“18–19 分钟/轮”是这一快照的近似描述，不是未来每轮或结束时间保证。

N/weight0 的另一来源是已完成的匹配 wrapper 控制：[既有吞吐核对](../../2026-09-08_ops_训练吞吐诊断/THROUGHPUT_HISTORY.md)。seed42 CSV 末值为 41414.7 秒，即 11.504083 小时；其 completion 为 41428.191229 秒，约多 13.49 秒，计时边界保持分列。另两个 N seeds 的 CSV 分别约 12.1146/11.9629 小时，因此不能把“约 11 小时”当作所有 N 运行的固定耗时。直接来源为 `../../2026-09-07_train_IndependentKD实施/snapshots/2026-09-07T165357.033246_0800/raw/N42/{args.yaml,results.csv,completion_receipt.json}`。

这些 args 都记录 B32、nbs64、640、SGD、AMP、seed42 和通用 YOLO11n 初始化；原 baseline 使用 workers8，当前 C1 及上述 N/weight0 使用 workers4。N/weight0 本身的已完成耗时已经高于原 RGB baseline，说明不能把“原始单模态入口→当前 C1”的整个差额直接标成 KD 算子成本。workers、数据/跟踪 wrapper、具体选择实现与共享 CPU/GPU/存储及运行时段均未在这些 CSV 中被隔离；也不能只凭 workers8→4 就给出其耗时贡献。

若仅作描述性算术，最近十轮中位数之比为 `1111.75 / 61.4 ≈ 18.11`。这个比值横跨不同入口、时间、训练进度和共享负载，既不是同负载代码 benchmark，也不能拆成教师前向、池化、KD 或 dataloader 的因果份额。此前局部算子/同 raw 回放以及 24-update 验证另有独立证据，不能用它们把这里的整段历史差额自动归因。

本次整理的作用是纠正等待时间的参照：完整原 baseline 实际只需数小时，而当前正式 C1 的历史逐轮耗时显著更高。它支持另建已授权的小时级筛查来缩短反馈周期，不提供新 AP 或方法收益判断，也没有修改或停止原 E200。采集入口为 [collect_baseline_runtime.py](../collect_baseline_runtime.py)；未加载 checkpoint、计算新文件 hash 或运行 GPU。
